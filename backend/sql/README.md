# Generated MySQL 5.7.24 schema

Current application head: `20261112_0009` (93 application tables). Apply migrations
with `python -m alembic upgrade head`; the historical 001 export below still ends
at 0002. Incremental exports 003, 004 and 005 add customer Meowsurement, optional
manual frames, and the loyalty/games/cashback/replacement domains respectively.
See [the feature runbook](../../docs/LOYALTY_GAMES_RMA.md) for configuration and
the verified 0005 installation.

`001_initial_schema.sql` is the full **fresh-database** export through Alembic
head `20261106_0002`. It applies the initial schema history `20261106_0001` and
the MySQL 5.7 compatibility revision. It contains the 68 application/support
tables, Alembic's version table, and validation triggers. No users, passwords,
demo products, or production records are inserted; only schema revision state
is written.

The Step 2 compatibility audit corrected the earlier export's unsupported
`point_logs.note TEXT DEFAULT ('')`. The new export uses `note TEXT NOT NULL`;
application code supplies an empty note when omitted. MySQL 5.7 cannot store
TEXT defaults. Do not reuse the earlier full SQL file. If it failed partway,
inspect the partial schema and use a new empty test database rather than
manually stamping a revision or deleting business data.

Normal installation, from `backend/` against a new empty dedicated Oracle
MySQL 5.7.24-log database (supported family: MySQL 5.7 patch 24 or later):

```bash
python -m alembic upgrade head
```

To inspect the SQL without a database or credentials:

```bash
python -m alembic upgrade head --sql
```

A DBA can apply this SQL directly after selecting the empty target database,
using the MySQL command-line client or a script runner that understands
`DELIMITER` directives, such as MySQL Workbench. Those directives let the client
send a complete trigger body; they are not SQL statements sent to the server.
Online Alembic execution sends trigger statements directly through the driver
and does not send `DELIMITER` commands.

Do not reapply the full export to a populated schema. Commit the final revision
INSERT/UPDATE if the SQL client has autocommit disabled. The script does not
create the database, users or grants, and is not a MongoDB data converter.

MySQL 5.7 does not enforce native CHECK predicates. The compatibility revision
uses `BEFORE INSERT` and `BEFORE UPDATE` triggers with `SIGNAL SQLSTATE '45000'`
to reject violations. The migration account needs the appropriate DDL and
`TRIGGER` privileges. Binary-logging policies on a managed server may require
the DBA to perform or authorize trigger installation; the script does not
change global trust or binary-log settings.

Keep the trigger definer account and its required table privileges after
installation. The normal runtime account can have ordinary data privileges;
the separate `python -m mysql.check_integrity` command uses a migration/verifier
account to audit data and trigger definitions.

For a supported target already recorded at `20261106_0001`, use Alembic:

```bash
python -m alembic current
python -m alembic upgrade head
```

The incremental offline export is `002_mysql57_compatibility.sql`, generated by:

```bash
python -m alembic upgrade 20261106_0001:20261106_0002 --sql
```

Online Alembic checks existing row predicates before installing the triggers.
The offline incremental SQL does not perform that automatic preflight. Before
using it on a populated target, pause all writers/jobs and run:

```bash
python -m mysql.check_integrity --preflight-only
```

Resolve violations, apply the incremental script with stop-on-error behavior,
and run `python -m mysql.check_integrity` before resuming writes. Never use
`mysql --force` to continue after installation errors. Prefer online Alembic
for resumable installation of the compatibility revision.

Do not stamp `0002` manually to skip installation. A server previously running
MySQL 8.4 is a separate migration concern: do not attach its data directory to
MySQL 5.7 or treat these schema revisions as a server downgrade tool.

Future model changes require a new Alembic revision. Do not edit an already
applied migration to force existing databases to match a new model.

Revision `20261111_0006` flattens product categories and seeds independent master
groups. It requires **online** Alembic because existing ancestry must be mapped
before dropping its columns. Historical SQL exports remain frozen; apply them
only to their recorded revision, then run `python -m alembic upgrade head` with
writers paused and a full backup. Full offline generation through `head` is
intentionally refused. See [the migration procedure](../../docs/mysql-migration/STEP_2.md#master-kategori-independen-0006).

Revision `20261112_0007` adds nullable `products.deleted_at` and the admin list
index. Existing products keep their status. Deletion hides a product from admin
and storefront lists while retaining order, stock, and measurement references;
deactivation keeps the product available in the admin list for reactivation.
The frozen incremental export is `007_product_deletion.sql`, generated with
`python -m alembic upgrade 20261111_0006:20261112_0007 --sql`. Apply it only to a
verified 0006 schema with backups; online `alembic upgrade head` is preferred.

Revision `20261112_0008` retires collection categories and product assignments,
archiving original references in a private setting. It requires online Alembic
and has no offline SQL export. It preserves materialized flash-sale prices and
quota while detaching their retired category rules. Back up before migration.

Revision `20261112_0009` adds nullable `stock_movements.ttb_number VARCHAR(128)`.
Existing stock quantities and historical movements remain unchanged. New
inventory adjustments record Receipt Stock/Issue Stock and the TTB reference.
